# Agent Instructions

- Keep controllers and models slim. Use CRUD actions for resource changes; use `update` for edits to the same resource, and introduce a clearly named resource controller only when the action is genuinely distinct. Keep controllers resource-oriented: expose the requested resource or collection, and let views access associations through that entity rather than extracting them into presentation-only instance variables.
- Keep controller private methods in the HTTP/request layer or use them to invoke model and concept APIs. Put relation construction, eligibility rules, and reusable query composition in clearly named model scopes.
- Prefer obvious, application-specific Rails code over defensive abstractions for hypothetical inputs. Use documented public framework APIs, not lower-level implementation details.
- Prefer Rails conventions over client-side requests: use forms, including hidden forms when appropriate, and use `requestSubmit` when JavaScript must submit one. Do not hand-roll requests, authenticity tokens, or CSRF workarounds.
- Use concepts only when they clarify ownership. Their directory must match the defining namespace and follow Rails autoloading conventions; for example, `app/concepts/charts/service.rb` defines `Charts::Service`. Name files for their role or pattern, such as `service`, `builder`, `factory`, `adapter`, `util`, or `presenter`, not for business rules.
- A service holds business logic for an entity or concept. For logic spanning concepts, choose the concept the action serves; if ownership remains unclear, introduce a new concept and service. Adapters isolate external dependencies and contain no business logic. Builders, factories, and similar objects should follow their established pattern and Rails naming conventions. Use concerns when appropriate, but avoid unnecessary extra nesting.
- Keep HTML in views, not JavaScript or helpers. Use template tags to show or hide existing markup. Helpers may return small, clearly named presentation data or paths, but not HTML. Put entity-specific helpers in the matching helper module and name them with the entity first, such as `post_primary_translation`.
- Avoid local assignments in ERB unless required by the template API or repeated access to an association or derived value makes a named local clearer. Use a helper for a small presentation computation; use a presenter when a view needs several related values or rules outside the model. If presenters become numerous or composable, introduce a consistent view-model or component layer, such as ViewComponent.
- Prefer small, well-known, documented dependencies over custom implementations. When a dependency's documented interface generates its own UI, use it declaratively in ERB rather than recreating its markup in JavaScript; review its license, accessibility, styling, and asset-loading requirements first.
- Do not improvise assets like: audio, videos, icons, graphs, illustrations, or image sources with Unicode, arbitrary markup, or placeholder services. Ask which icon library or image service to use when the project has not established one. This project uses Lucide for application UI icons; retain meaningful text labels and mark decorative icons as hidden from assistive technology.
- Use migrations only for schema changes. Perform data fixes and backfills with idempotent Rake tasks that can run safely in phases.
